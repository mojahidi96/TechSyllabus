# How do you scale Node.js?

I usually think about scaling Node.js in layers. **First make one instance efficient**, then use all CPU cores, then scale horizontally, and finally remove the bottlenecks around Node, like the database and heavy background work. And as always, I start by measuring with **load tests**, using tools like _k6_ or _Artillery_, so we know where it actually breaks.

**1. Make one instance efficient.**

- Keep the event loop free. No sync calls or heavy computation in request handlers.
- Move CPU-heavy tasks to worker threads.
- Use streams for large files and payloads instead of loading everything into memory.

Most Node ‘scaling’ issues I’ve seen were really a blocked event loop.

**2. Use all CPU cores.**
A single Node process uses one core. To use the whole machine, run multiple processes with the _cluster module_ or _PM2_. In containers, the more common pattern is one process per container, with more containers instead.

**3. Scale horizontally.**

- Run multiple instances behind a load balancer, like Nginx or AWS ALB.
- Use Kubernetes or ECS with autoscaling, based on CPU, memory, or request rate.
- The key requirement is that the app must be stateless. No sessions or uploads stored in memory or on local disk.
  - Sessions go into Redis, or use JWT.
  - Files go to S3 or similar object storage.
  - For WebSockets, use sticky sessions plus the Redis adapter, so messages reach users connected to other instances.

**4. Caching.**

- Redis for frequently read data, sessions, and computed results.
- CDN for static assets and cacheable API responses.
- Proper HTTP cache headers.

Often caching gives a bigger win than adding servers.

**5. Fix the database bottleneck.**
In my experience, the database usually becomes the limit before Node does.

- Connection pooling.
- Indexes and query optimization.
- Read replicas for read-heavy traffic.
- Sharding or partitioning only at very large scale.

**6. Offload work asynchronously.**

Anything that doesn’t need to happen within the request, like emails, reports, image processing, or notifications, goes to a message queue such as **BullMQ**, **RabbitMQ**, or **Kafka**, and is processed by separate workers. That keeps API response times low and lets workers scale independently.

**7. Resilience.**

- **Rate limiting** to protect against abuse and traffic spikes.
- **Timeouts and circuit breakers** for downstream services.
- **Health checks and graceful shutdown**, so deployments and autoscaling don’t drop requests.

**8. Observability.**

- APM tools like Datadog, New Relic, or OpenTelemetry.
- Structured logs.
- Metrics like latency, error rate, and **event loop lag.**

You can’t scale what you can’t see.

At the architecture level, if one part of the system has very different load, like a search or reporting service, I’d split it into its own service so it can scale independently. But I wouldn’t jump to microservices just for scaling. A well-built, stateless service behind a load balancer goes a very long way.

For example, on one project our Angular SSR server struggled during traffic spikes. We made it stateless, ran it in containers with autoscaling, added Redis caching for rendered pages and API data, and put a CDN in front. Response times became stable even at several times the earlier traffic, and we actually used fewer servers on normal days.”
