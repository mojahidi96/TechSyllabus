# Q4 API security

I’ll cover this in two parts: **how I secure the API overall**, and then **token storage**, which is one of the most debated topics on the frontend side.

## Part 1: API security

I think of it in layers. No single control is enough.

**1. Authentication: who are you?**

- Use _OAuth 2.0_ / _OpenID_ Connect with a proper identity provider like _Auth0_, _Azure AD_, _Okta_, or _Keycloak_, instead of building auth from scratch.
- For SPAs like Angular, use the Authorization Code flow with PKCE(Proof Key for Code Exchange). The implicit flow is outdated.
- Validate JWTs properly on every request: signature, expiry, issuer, audience, and allowed algorithm.
- Keep access tokens short-lived, _around 5 to 15 minutes_, and use refresh token _rotation_.

**2. Authorization: what are you allowed to do?**

- Role-based or attribute-based access control.
- Most importantly, object-level checks. It’s not enough to check ‘is the user logged in?’ You must check ‘does this user own order 123?’ Broken object-level - authorization is the number one risk in the OWASP API Top 10, and I’ve seen it in real code reviews more often than people expect.
- Always enforce on the server. Hiding a button in Angular is UX, not security.

**3. Input and output**

- Validate all input with _Zod_ or _class-validator_, and whitelist the allowed fields.
- Parameterized queries or an ORM to prevent injection.
- Never return more data than needed. No password hashes or internal fields in responses.
- Generic error messages to clients, with no stack traces.

**4. Transport and headers**

- HTTPS everywhere, with HSTS.
- Strict CORS with an allowlist of origins, never `*` with credentials.
- Security headers with Helmet, including a Content Security Policy.

**5. Abuse protection**

- Rate limiting and throttling, especially on login, OTP, and password reset endpoints.
- Payload size limits.

**6. Secrets and dependencies**

- Secrets in a vault or secret manager, not in code or committed .env files.
- Dependency scanning with npm audit, Snyk, or Dependabot in CI.

**7. Monitoring**

- Log authentication failures and suspicious activity, but never log tokens or personal data.
- Set up alerts and audit trails.

## Part 2: Where should the access token be stored?

There’s no perfect option, so I’d explain the trade-offs and then my recommendation.

**localStorage / sessionStorage Readable by any JavaScript**, so one `XSS` bug means the token is stolen. Simple, but the weakest option.
**In memory** (a variable or signal in a service) Much safer against XSS persistence, _but lost on page refresh_, so you need a silent refresh mechanism.
**HttpOnly**, Secure, SameSite cookie JavaScript can’t read it, so it’s protected from XSS theft. You need to handle CSRF, with SameSite plus a CSRF token.

**My recommendation, in order of preference:**

1.  The BFF pattern, Backend for Frontend. This is the most secure option and what the current OAuth guidance for browser apps recommends. The tokens never reach the browser at all. A small Node backend does the OAuth flow, keeps the tokens on the server, and gives the browser only an HttpOnly, Secure, SameSite session cookie. The Angular app just calls the BFF. This is what I’d use for anything sensitive, like banking, healthcare, or enterprise apps.

2.  If there’s no BFF: keep the access token in memory, and the refresh token in an HttpOnly, Secure, SameSite=Strict cookie with rotation. On page refresh, the app silently calls the refresh endpoint to get a new access token.

3.  Avoid localStorage for anything sensitive. If a team uses it, short-lived tokens and a strong CSP become even more important.

On the Angular side:

An HTTP interceptor attaches the token and handles 401 responses, with only one refresh call in flight at a time while other requests wait. Otherwise you get a flood of refresh calls.
XSS prevention, because storage choice doesn’t matter if the app has XSS. Rely on Angular’s built-in sanitization, avoid bypassSecurityTrust... and innerHTML with user data, and add a strict CSP.

In one project, the app was storing JWTs in localStorage with 24-hour expiry. During a security audit, this was flagged as high risk. I proposed moving to a BFF with HttpOnly cookies. We rolled it out behind a feature flag, so the login flow could be switched back if needed. I also added a lint rule blocking bypassSecurityTrust without review. The next penetration test came back clean on authentication, and it became our standard for new apps.”
