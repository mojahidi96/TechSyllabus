## Q1. Explain Node.js event loop.

The event loop is what lets Node.js handle thousands of concurrent requests with a single JavaScript thread. JavaScript runs on one thread, but slow work like file and network I/O is handed off to the system, and the event loop picks up the callbacks when that work is done.

The main points are: **the single thread and libuv, the phases of the loop, microtasks,** and why you must never block the loop.

**1. Single thread and libuv.** Node runs our JavaScript on one main thread. The heavy lifting is done by libuv, a C library underneath:

- Network I/O is handled by the operating system’s async mechanisms, like epoll on Linux.
- File system, DNS lookup, crypto, and compression use libuv’s thread pool, which has 4 threads by default and is configurable with `UV_THREADPOOL_SIZE`.

**When the work finishes, its callback is queued, and the event loop runs it on the main thread.**

### 2. The phases. Each iteration, or tick, of the loop goes through phases in order:

**Timers**: runs setTimeout and setInterval callbacks whose time has expired.
**Pending callbacks**: some deferred system-level callbacks.
**Poll**: the most important phase. It waits for new I/O events and runs their callbacks, like an incoming request or a file read completing.
**Check:** runs setImmediate callbacks.
**Close callbacks:** for example, socket close events.

### 3. Microtasks. These run between callbacks, not in a phase. After every callback, Node drains:

the `process.nextTick` queue first,
then the promise microtask queue (.then, await).

So _promises_ and _nextTick_ always run before the loop moves on. Overusing nextTick recursively can actually starve the event loop.

**A classic example:**

js

```
console.log('1');
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
Promise.resolve().then(() => console.log('promise'));
process.nextTick(() => console.log('nextTick'));
console.log('2');
```

The output is `1`, `2`, `nextTick`, `promise`, and then `timeout` and `immediate`. Interestingly, the order of timeout and immediate isn’t guaranteed in the _main module_, but inside an I/O callback, setImmediate always runs first.

### 4. Don’t block the event loop. Since there’s only one JS thread, one slow synchronous task blocks every user. Common culprits are:

- heavy loops or calculations,
- `JSON.parse` on huge payloads,
- sync APIs like `fs.readFileSync` inside request handlers,
- badly written regular expressions.

**Solutions:**

- Move CPU-heavy work to _worker threads_, or a separate service or queue.
- Use async APIs.
- Process large data in chunks or with streams.
- Monitor event loop lag with _perf_hooks.monitorEventLoopDelay_ or an APM tool.

This is relevant for me as a frontend lead too, because Angular SSR runs on Node. On one project, our SSR server response time spiked under load. Profiling showed a large synchronous data transformation running on every request. We moved it to a cached, precomputed step, and latency went back to normal. That was a good lesson that in Node, one blocking function affects everyone.”
