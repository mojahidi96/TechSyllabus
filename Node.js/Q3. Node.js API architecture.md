# Q. Explain Node.js API architecture

For a Node.js API, my main goal is a structure where business logic is separate from the **framework** and the **database**, so it’s easy to test, easy to change, and easy for a growing team to work in.

The key points are: a layered architecture, feature-based modules, cross-cutting concerns handled centrally, good API design, and production readiness.

**1. Layered architecture. Each request flows through clear layers:**

- **Routes and controllers handle HTTP only**: read the request, call a service, and return a response. No business logic here.
- **Services hold the business logic**: rules, calculations, and orchestration.
- **Repositories or data access** handle database queries, through an ORM like Prisma or TypeORM, or raw queries.
- **Models and DTOs** define the shape of data going in and out.

The benefit is that I can test services without HTTP, or switch the database without touching business logic.

**2. Organize by feature.** Same principle as in Angular. Instead of global `controllers/` and `services/` folders, I group by domain, like `users/`, `orders/`, and `payments/`, each with its own controller, service, repository, and validation. Shared things go into a `common/` or `core/` folder.

**3. Framework choice.**

Express or Fastify for smaller or simpler services. Fastify is faster and has built-in schema validation.
NestJS for large apps and bigger teams. It enforces modules, dependency injection, and a clear structure, and it feels very familiar to Angular developers. That makes it a good fit when the same team works on both frontend and backend.

**4. Cross-cutting concerns, handled centrally:**

- _Authentication_ and _authorization_ in middleware or guards, using JWT or OAuth, plus role-based access.
- Validation at the entry point with Zod or class-validator. Never trust input.
- A centralized error handler with custom error classes and a consistent error response format, so no stack traces leak to clients.
- Structured logging with _Pino_ and a correlation ID per request, so we can trace a request across services.
- Config from environment variables, validated at startup so the app fails fast if something is missing.
- _Security:_ Helmet, CORS, rate limiting, and parameterized queries.

5. API design.

- Consistent REST conventions, with proper resource names, HTTP methods, and status codes.
- Versioning (/api/v1) so we don’t break clients.
- Pagination, filtering, and sorting for list endpoints.
- A consistent response and error format.
- OpenAPI or Swagger docs, ideally generated from code. We then generate TypeScript clients for the Angular app, so frontend and backend types never drift.

6. Production readiness.

- Stateless, so it scales horizontally.
- Caching with Redis, and queues for background work like emails and reports.
- Health checks and graceful shutdown.
- Observability: metrics, tracing, and logs.
- Testing: unit tests for services, integration tests with Supertest, and contract tests between services.

7. Overall architecture. I usually start with a modular monolith: one deployable app with strong module boundaries. It’s simpler to build, deploy, and debug. If a module later needs independent scaling or a separate team, it’s easy to extract it into a microservice, because the boundaries already exist. As a frontend lead, I also like the BFF pattern, Backend for Frontend: a thin Node layer that aggregates multiple backend services and shapes data exactly for the UI. That keeps the Angular app simpler and reduces API calls.

On one project, we had controllers with 500 lines of mixed business logic and SQL, and every change broke something. I proposed a refactor to a layered NestJS structure, with module by module migration so we didn’t stop feature work. I also set up shared conventions for errors, logging, and validation, and generated typed API clients for the Angular app. After that, onboarding new developers became much faster, and bugs from frontend-backend mismatches dropped significantly.”
