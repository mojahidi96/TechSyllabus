# Explain Angular change detection.

Change detection is how Angular keeps the UI in sync with the component’s data. When something changes, Angular checks the component tree and updates the DOM wherever a bound value is different.

**What triggers it.** Traditionally, Angular uses Zone.js, which patches async APIs like click events, `setTimeout`, promises, and HTTP calls. Whenever one of those completes, Zone.js tells Angular something might have changed, and Angular runs change detection.

**How it runs.** Angular walks the component tree top-down, from the root to the leaves. For each component, it compares the current template binding values with the previous ones, and if something changed, it updates only that part of the DOM. In dev mode, it runs a second check to make sure nothing changed during the first pass. That’s where the `ExpressionChangedAfterItHasBeenChecked` error comes from.

**Default vs OnPush.** With the Default strategy, every component is checked on every cycle, which gets expensive in large apps. With OnPush, Angular skips a component and its subtree unless:

- an `@Input` reference changes,
- an event fires inside that component,
- the `async` pipe emits,
- a signal read in the template changes,
- or we call `markForCheck()` manually.

That’s why OnPush works best with immutable data. If you mutate an object instead of creating a new reference, the view won’t update.

**Signals and zoneless.** This is the big shift in modern Angular. With signals, Angular knows exactly which component depends on which value, so it can update just that component instead of checking the whole tree. And with zoneless change detection, which is stable now, we can remove Zone.js entirely. Change detection is then triggered by signals, the async pipe, or `markForCheck`, not by every browser event. That means smaller bundles, better performance, and easier debugging.

**In practice,** I’ve used it like this:

- OnPush is the default in every new component, and zoneless with signals on new apps.
- Avoid function calls in templates; use `computed` signals or pure pipes instead.
- Use `track` in `@for` loops.
- Run heavy third-party code, like charts or scroll listeners, outside Angular with `runOutsideAngular`.
