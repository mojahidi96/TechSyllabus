# Q4. How would you improve performance of a large Angular application?

The first thing I’d say is: **measure before optimizing**. In large apps, the real problem is often not where people assume. So I start with Lighthouse and Core Web Vitals for load performance, Angular DevTools profiler for change detection, and a bundle analyzer to see what’s actually inside the build.

Then I look at performance in four areas: _initial load_, _runtime rendering_, _network_, and _memory_.

**1. Initial load:** reduce what the user downloads.

- Lazy load every feature route, so the user only downloads what they need.
- Use `@defer` for heavy sections like charts, editors, or below-the-fold content.
- Audit the bundle. I’ve often found things like a full Moment.js or Lodash import, or a big chart library used on one page. Replacing or lazy loading those gives quick wins.
- Use standalone components and the esbuild-based builder for better tree-shaking and faster builds.
- Use `NgOptimizedImage` for lazy loading images, correct sizing, and priority hints for LCP images.
- Choose a preloading strategy wisely, preloading only routes the user is likely to visit next.
- For public-facing or SEO-heavy apps, use SSR with hydration, and now incremental hydration, so the page shows fast and becomes interactive piece by piece.

**2. Runtime rendering:** make change detection cheap.

- OnPush everywhere, and on newer apps signals with zoneless, so only affected components update.
- No function calls in templates; use `computed()` or pure pipes.
- Always use track in `@for` loops so Angular doesn’t recreate DOM nodes unnecessarily.
- Virtual scrolling with CDK for large lists and tables, so we render 20 rows, not 10,000.
- Run heavy third-party libraries, scroll or mousemove listeners outside Angular with `runOutsideAngular`.
- Move CPU-heavy work, like large data processing, to **Web Workers**.

**3. Network:** fewer and smarter calls.

- Cache data that doesn’t change often, at the service level or with an HTTP interceptor, and use `shareReplay` to avoid duplicate calls.
- Use `debounceTime` and `switchMap` on search so we cancel stale requests.
- Use server-side pagination and filtering instead of loading everything to the client.
- Make sure the _CDN_, _compression (gzip or Brotli)_, and _caching headers_ are set correctly.

**4. Memory:** avoid leaks.

- Use `takeUntilDestroyed()`, `toSignal()`, or the async pipe instead of manual subscriptions.
- Clean up event listeners, timers, and third-party instances in `DestroyRef` or `ngOnDestroy`.
- Use _Chrome memory snapshots_ to catch components that never get garbage collected.

**Finally, make it sustainable. **Performance fixes don’t last unless they’re guarded. So I add bundle budgets in CI, Lighthouse checks in the pipeline, and real user monitoring in production, so we catch regressions early.

For example, on one enterprise app the main bundle was around 4 MB and the dashboard took several seconds to become usable. We lazy loaded the modules, removed a couple of heavy libraries, deferred the charts, and moved the grids to OnPush with virtual scrolling. The initial bundle dropped by more than half, and the dashboard felt instant compared to before. After that, the budgets in CI stopped it from creeping back up.”
