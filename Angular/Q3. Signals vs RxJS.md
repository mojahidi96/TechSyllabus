# Q3. When would you use Signals vs RxJS?

**signals for state**, **RxJS for async streams and events.** They’re not competitors; they solve different problems, and in a modern Angular app I use both together.

**When I use signals:**

- **Component and UI state,** like a selected tab, a loading flag, form visibility, or a list of items in a store.
- **Derived values,** with `computed()`. For example, filtering a list or calculating a total. It’s memoized and updates automatically.
- **Template bindings.** Signals give fine-grained change detection and work naturally with OnPush and zoneless.
- **Synchronous, current-value data,** meaning “what is the value right now?”

They’re simpler: no subscriptions, no memory leaks, and much easier for junior developers to read.

**When I use RxJS:**

- **Async streams over time**, like WebSockets, server-sent events, or polling.
- **Complex timing and coordination.** `debounceTime` on search, `switchMap` to cancel previous requests, `retry` with backoff, and `combineLatest` or `forkJoin` across multiple APIs.
- **Event-driven flows,** where how and when things happen matters, not just the latest value.

Signals don’t have operators like debounce or cancellation, so trying to do that with signals and effects gets messy quickly.

**Things I avoid:**

Using `BehaviorSubject` just to hold simple state. That’s a signal now.
Using `effect()` to sync one signal into another. That should be `computed()`.
Manual `.subscribe()` in components when `toSignal()` or the async pipe can handle it.

In our last project, we moved most of the store state from BehaviorSubjects to signals. The code got noticeably shorter and easier to follow, but we kept RxJS in the API layer and for the real-time notifications, because that’s where it really shines.”

Q3. Signals vs RxJS

One-liner: Signals for state, RxJS for async streams/events. They complement each other.

Use signals for:

UI and component state (flags, selections, store state)
Derived values with computed()
Template binding (fine-grained, zoneless-friendly)
Current value, synchronous
No subscriptions, no leaks, simpler code

Use RxJS for:

Streams over time (WebSockets, polling, SSE)
Timing and coordination: debounceTime, switchMap (cancel), retry, combineLatest, forkJoin
Event-driven flows

Combine:

RxJS for the async logic, then toSignal() for the template
toObservable() for the reverse direction
resource, rxResource, httpResource for data loading
Example: search box with debounce, then switchMap, then toSignal()

Avoid:

BehaviorSubject for simple state (use a signal)
effect() to derive state (use computed())
Manual .subscribe() in components
