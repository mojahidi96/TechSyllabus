# Q5. When would you use micro-frontends vs micro-frontends?

My view is that **micro-frontends solve an organizational problem more than a technical one.** If the problem is ‘multiple teams are blocking each other’s releases,’ micro-frontends can help. If the problem is ‘our code is messy,’ they usually make it worse.

### When I would use micro-frontends:

- **Multiple independent teams that need independent deployments.** For example, five or six teams, each owning a business area like _payments_, _orders_, or _reporting_.
- **If one team’s release is blocked by another team’s bug**, that’s the real pain micro-frontends solve.
- **Different release cycles**. One area ships daily while another is tightly regulated and ships monthly.
- **Legacy migration**. This is one of the best use cases. When moving from AngularJS, or an old Angular version, to modern Angular, we can use the strangler pattern: build new features as separate micro-frontends and gradually replace the old app, instead of doing a risky big-bang rewrite.
- **Integrating apps from different teams or acquisitions**, possibly on different frameworks or versions, into one product shell.
- **Clearly separated domains** with little shared UI state between them.

### When I would NOT use them:

- **Small or medium teams.** If one or two teams own the whole app, the overhead isn’t worth it.
- **When the real issue is code organization.** A well-structured **Nx monorepo** with enforced boundaries gives most of the benefits, like modularity and team ownership, without the runtime complexity.
- **Tightly coupled features that share a lot of state or need constant communication.** Splitting them just creates a distributed monolith.
- **When performance is critical,** because duplicated dependencies and extra network requests can hurt load time.
- **When strict UX consistency is required** and there’s no strong shared design system.
- **When DevOps maturity is low.** Micro-frontends need solid CI/CD, versioning, monitoring, and environment management.

### The hidden costs people underestimate:

- shared dependency version conflicts, especially Angular versions
- duplicated bundles
- cross-app communication
- routing and authentication across apps
- end-to-end testing
- debugging production issues across multiple deployments

### If I do go with micro-frontends, I keep a few rules:

- A shell app that handles layout, routing, and authentication.
- Native Federation or Module Federation, with Angular core and the design system as shared singletons.
- Minimal communication between micro-frontends, through URL params, custom events, or a small shared contract, never a shared global store.
- Independent CI/CD per micro-frontend, but common standards for versions, linting, and design.

On one project, we had a large AngularJS application and couldn’t afford a full rewrite. We created an Angular shell and migrated feature by feature as separate micro-frontends. That let the business keep shipping while we modernized. But on another project, with a single team of eight developers, someone proposed micro-frontends. We went with an Nx monorepo instead, and it was the right call. We got clean boundaries without the operational overhead.”

Q5. Micro-frontends: when to use and when not

Key line: Micro-frontends solve an organizational problem, not a code-quality problem.

Use when:

Multiple independent teams need independent deployments
Different release cycles per domain
Legacy migration with the strangler pattern (AngularJS to Angular)
Integrating apps from different teams, tech stacks, or acquisitions
Loosely coupled domains

Don’t use when:

Small or medium team (1–2 teams)
The problem is code organization (use an Nx monorepo)
Features are tightly coupled (you get a distributed monolith)
Performance is critical (duplicate bundles)
There’s no strong design system (inconsistent UX)
DevOps maturity is low

Hidden costs:

Version conflicts, duplicate dependencies
Communication, routing, and auth across apps
E2E testing and debugging

If used:

Shell app for layout, routing, and auth
Native or Module Federation with shared singletons (Angular, design system)
Communicate via URL or custom events, no shared global store
Independent CI/CD with common standards

Examples:

AngularJS migration: shell plus feature-by-feature micro-frontends
Single team of 8: chose an Nx monorepo instead
