# Q1. How would you architect a large Angular application?

How many teams will work on this,
how long will it live,
and does it need SEO or offline support?
Those answers drive most of the decisions. Speaking generally, though, from what I’ve built over the years, I focus on six things:

1. **Domain-driven structure**: organize by business feature, not by file type
2. **Clear boundaries and dependency rules**, enforced by tooling rather than goodwill
3. **A deliberate state management strategy**
4. **Performance built in from day one**: lazy loading, OnPush, signals
5. **A shared design system and a core layer**
6. **Developer experience and governance:** monorepo, CI, testing, standards

**Structure.** Early in my career I worked on apps with `components/`, `services/`, and `models/` folders at the root. That works for 20 screens and becomes painful at 200. Now I always structure around business domains, such as orders, billing, and user management. Each domain is self-contained and owns its routes, its state, and its UI. If a team owns billing, they mostly live inside that one folder.

**Boundaries.** For anything large I use an Nx monorepo and split each domain into libraries by type:

- **Feature** libraries hold the smart, routed components.
- **UI** libraries hold dumb, presentational components.
- **Data-access** libraries hold services, API calls, and state.
- **Util** libraries hold pure functions.

**State.** I’m fairly _pragmatic_ here. I don’t put NgRx on everything by default anymore. With signals now mature, most local and feature-level state is handled well by signal-based services or NgRx SignalStore.
I reach for full NgRx with actions and effects only when there’s complex, shared, event-driven state, or when the team benefits from strict traceability, for example in a trading or workflow-heavy app. The main rule is one clear source of truth per piece of data, and components never call HTTP directly.

**Performance.** Everything is standalone components now, with lazy-loaded routes per domain, `@defer` blocks for heavy below-the-fold content, and OnPush change detection everywhere. On newer apps I go zoneless with signals, which has given a noticeable boost in runtime performance and makes change detection much more predictable. I also set bundle budgets in the CI config so that if someone pulls in a 300 KB library, the build fails and we have that conversation early, not after users complain.

**Core and shared layer.** I set up one place for cross-cutting concerns: functional HTTP interceptors for auth tokens, error handling, and retries; a global error handler wired to monitoring like Sentry; route guards; and environment config. Alongside that, a design system library, ideally with Storybook, so twenty developers aren’t building twenty slightly different buttons.

**Scaling teams.** If multiple teams need to deploy independently, I’d consider micro-frontends with Module Federation or Native Federation. But I’m cautious about this. I’ve seen teams adopt micro-frontends because it sounded modern, and then spend months fighting shared dependency versions and inconsistent UX. If the teams can work in one monorepo with good boundaries, that’s usually the simpler and better choice. Micro-frontends solve an organizational problem more than a technical one.

**Governance.** The architecture only survives if it’s enforced:

- strict TypeScript
- ESLint with architecture rules
- Nx affected builds so CI stays fast as the repo grows
- unit tests with Jest or Vitest on business logic, and Playwright for critical user journeys
- short Architecture Decision Record (ADR), or architecture decision records, so that two years later people know _why_ we made a choice, not just what it was

Start with: Understand the context first: team size, app lifespan, and business needs.

1. Domain-based structure

Organize by feature (orders, payments, users), not by file type
Each domain owns its routes, components, and state

2. Enforce boundaries

Nx monorepo with feature, UI, data-access, and util libraries
Lint rules block wrong imports

3. State management

Signals or SignalStore for most cases
NgRx only for complex shared state
No API calls or business logic in components

4. Performance by default

Standalone components, lazy loading, @defer
OnPush or zoneless change detection with signals
Bundle budgets in CI

5. Core and shared layer

Interceptors (auth, errors), guards, global error logging
Shared design system for a consistent UI

6. Governance

Strict TypeScript, ESLint, tests (Jest/Vitest, Playwright)
CI that builds only what changed
ADRs to document decisions

Micro-frontends: Only when teams need independent deployment.

Closing line: “Organize by domain, enforce boundaries, keep state predictable, make performance the default, and add guardrails so it scales with the team.”
